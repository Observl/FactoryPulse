# FactoryPulse

**面向制造企业设备主管与维修团队，把设备风险转化为可执行、可追踪的维护安排。**

设备出现异常后，真正需要解决的是：**先查哪台、为什么要查、什么时候能修、由谁来修、修完如何验收。** FactoryPulse 将监测数据、风险证据、生产占用、维修资源和工单协作连接起来，帮助团队完成从发现问题到维修闭环的全过程。

[在线入口](https://factorypulse.griffonage2077.workers.dev) · [使用流程](#如何使用从数据到维修闭环) · [本地启动](#本地启动) · [部署说明](docs/CLOUD-DEPLOYMENT.md)

![FactoryPulse 设备维护工作台](docs/images/dashboard.png)

> 当前定位为工程验证与业务流程演练应用。软件验收采用冻结的合成机床数据；真实工厂的预测效果、停机改善和经济收益仍待现场验证。线上入口的功能范围与完整部署存在差异，见下方说明。

## 谁会使用它

| 目标用户 | 日常问题 | 在 FactoryPulse 中完成什么 |
| --- | --- | --- |
| **设备主管、设备管理人员**（核心用户） | 异常很多，先处理哪个？维修会不会影响生产？ | 复核设备证据、创建维护需求、比较安排、审批与验收 |
| **维修班组与维修人员** | 今天修什么？何时开工？结果交给谁？ | 查看个人工单、接单、开工、暂停与恢复、提交维修结果 |
| **部署与系统维护人员** | 如何配置账号、数据与计算服务？ | 管理权限、接入数据、配置 AI 与服务、检查运行记录 |
| **只读查看人员** | 如何了解设备和维修进展？ | 查询设备状态、风险证据、工单进度和维修履历 |

适合需要把**设备监测与维修协作接起来**的制造业维护场景，也可用于预测性维护与约束排程的工程演练。使用企业数据时，需要先核对字段、时间、单位及实际维修资源。

## 核心思路与创新点

### 1. 风险证据直接进入维护决策

从设备风险页可以继续复核、转为维护需求、生成安排，直到审批、维修和验收。设备、数据版本、需求、方案及处理记录相互关联，便于追查一次维修为什么发生、依据是什么、最终如何处理。

### 2. 排程同时考虑“该修”与“能修”

维护优先级需要与人员技能、班次、设备停机窗口、生产订单占用、备件、预算和工时一起考虑。系统列出缺项与冲突，帮助主管判断需要补资源还是调整安排。

Python 计算服务提供 **OR-Tools CP-SAT 联合排程与三方案比较**；Workers 原生排程采用**按优先级逐任务寻找最早可行人员与时间**的策略。两者求解方式不同，可行方案不自动等于全局最优方案。

### 3. 分数有解释，证据有来源

设备页面可查看监测趋势、规则依据、EWMA 变化和 XGBoost 模型的 SHAP 特征贡献，并查看评分计算方式。模型可用时直接使用模型分排序；模型不足时明确显示趋势或规则参考，帮助使用者判断是否值得进一步检查。

### 4. AI 辅助查询与草拟，操作受权限控制

内置助手支持证据查询、维修需求和排程草案；Agent Harness 提供工具选择、会话恢复、记忆、一次性授权与审计机制。正式业务仍遵循角色权限及人工审批流程。悬浮助手还支持接入已发布的 Dify Workflow，其业务工具权限需在工作流中配置。

### 5. 执行变化后重新核对，验收形成闭环

批准后的工单在接单和首次开工时仍会核对版本与资源条件。完工后进入待验收；验收处理实际备件耗用、剩余预留及维修履历。不合格可退回维修，方便持续跟进处理结果。

## 如何使用：从数据到维修闭环

```mermaid
flowchart LR
    A[登录与核对数据] --> B[配置维修资源]
    B --> C[查看风险并复核]
    C --> D[创建维护需求]
    D --> E[生成与核对排程]
    E --> F[主管审批]
    F --> G[维修人员执行]
    G --> H[主管验收]
    H --> I[查看履历与复盘]
    H -->|不合格| G
```

### 第一步：登录并确认数据来源

使用分配的数字用户编号和密码登录，首次登录按五步教程熟悉界面。先核对当前数据版本、设备数量、监测时间和来源；历史数据的页面刷新不代表正在实时采集。

体验使用冻结验证集；接入企业数据时，在数据中心上传 **CSV/XLSX**，核对字段映射、单位、设备编号与采集时间，检查解析结果和数据质量，再确认启用。当前运行路径不支持直接导入 SQLite 文件；已有数据库应先导出 CSV/XLSX。

### 第二步：补齐维修资源与生产条件

在维护中心录入或核对：

- 设备检修动作、所需技能、人数、工时、费用与允许停机窗口。
- 维修人员技能、班次和可用工时。
- 生产订单的设备占用、备件实盘与已有预留。
- 本轮预算、并行人数和累计维修工时上限。

这些条件决定安排能否执行。演练资源必须与现场真实资源区分。

### 第三步：查看风险，决定是否需要维修

从工作台、设备台账或风险中心打开设备详情，查看异常指标、监测时间、风险变化、模型解释及维修历史。主管可以确认、驳回或延期复核；需要维修时转为维护需求，也可根据现场检查主动创建人工需求。

**确认预警表示已复核，并不表示已经维修。** 证据不足时应保留待评估状态。

### 第四步：生成安排并提交审批

核对维护需求的动作、技能、工时、备件和截止时间，再生成排程。有 Python 计算服务时，可在相同资源条件下比较三种方案。检查人员、起止时间、生产占用、预算与未安排原因，主管据此批准或退回。

条件或数据版本变化后，可能需要重新排程与审批；缺项和冲突需要处理后再继续。

### 第五步：维修人员执行工单

维修人员在“我的待办”查看分配给自己的任务，按实际情况依次接单、开工；需要中断时记录暂停与恢复。完成后提交维修结果、实际工时和费用，工单进入待验收。

### 第六步：验收、记录耗用并复盘

主管核对维修结果和实际备件耗用，验收通过后记录维修履历、扣减实际耗用并释放剩余预留；不合格则退回维修。后续可从设备详情、工单和操作追溯中查询处理过程，结合后续运行数据评估结果。

完整细节见 [操作手册](docs/OPERATOR-GUIDE.md)；其中历史本地账号初始化与旧数据描述，以本 README 和当前部署文档为准。

## 在线体验与部署选择

[打开 FactoryPulse](https://factorypulse.griffonage2077.workers.dev)。使用已有账号登录；只有部署者显式配置只读访客账号后，才显示一键访客入口，没有默认公开管理员账号。

| 运行方式 | 能力与要求 |
| --- | --- |
| **线上 Workers 入口** | 提供前端、集中账号，以及已迁移的数据读取与原生工单功能；实际可用性取决于 D1 状态和部署配置 |
| **本地启动** | 本机运行 React/Python，账号及业务数据访问 Cloudflare D1；已迁移的工单接口可转发到同一 Worker，需网络与私有配置 |
| **完整云端部署** | 在 Workers/D1 基础上连接 Python 计算服务，提供 CP-SAT 三方案比较、模型训练与企业数据导入等能力 |

未迁移且未接入计算服务的接口可能返回未实现提示，不能将前端可访问等同于全部功能已上线。线上数据服务的已知状态与迁移记录见 [Cloudflare 业务说明](docs/CLOUDFLARE-BUSINESS.md)。

## 本地启动

推荐环境：**Windows、64 位 Python 3.12、Node.js 22+、pnpm 11.25.0**。后端依赖锁面向 Windows / Python 3.12，其他平台需另行验证。

### 1. 获取源码并安装依赖

```powershell
git clone https://github.com/Observl/FactoryPulse.git
cd FactoryPulse
py -3.12 -m venv .venv
.venv\Scripts\python.exe -m pip install -r backend/requirements.lock.txt
corepack pnpm install --frozen-lockfile
npm run build
```

如未启用 Corepack，可先安装 pnpm 11.25.0，再执行 `pnpm install --frozen-lockfile`。

### 2. 配置账号与业务数据连接

按 [部署说明](docs/CLOUD-DEPLOYMENT.md) 准备服务端私有文件：

- `.secrets/identity.json`：D1 账号中心配置。
- `.secrets/business.json`：D1 业务库配置。
- 配置引用的服务端令牌文件，以及已创建的登录账号。

也可通过 `FACTORYPULSE_IDENTITY_CONFIG` 和 `FACTORYPULSE_BUSINESS_CONFIG` 指定配置文件路径。缺少配置时启动失败，不会自动生成默认账号或回退到本地业务库。凭据不提交到 Git，不写入前端。

### 3. 启动应用

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/start-local.ps1
```

打开 **http://127.0.0.1:8000**，登录后按上方业务流程操作。启动脚本输出日志位置，请据此确认服务启动结果。

默认运行目录为 `%LOCALAPPDATA%\FactoryPulse\data`，用于日志、临时文件等运行产物；可用 `FACTORYPULSE_DATA_DIR` 调整。**账号及业务数据存于 D1**，该目录不是本地业务数据库。

### 开发运行

完成上述私有配置后，在两个终端分别执行：

```powershell
.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

```powershell
npm run web
```

前端地址为 **http://127.0.0.1:5173**，开发服务器将 `/api` 转发到后端，开发模式同样需要登录。服务器部署见 [完整云端部署](docs/CLOUD-DEPLOYMENT.md)。

## 技术实现

```text
React + TypeScript 工作台 / Electron 桌面外壳
                    │
           Cloudflare Workers
           账号、原生工单、API 路由
              │             │
       Cloudflare D1    Python / FastAPI 计算服务
       账号库与业务库     模型分析、导入、CP-SAT 比较
                            │
                       同一 D1 业务数据
```

本地开发也可通过 FastAPI 作为入口；具体请求路径按部署配置确定。

| 层次 | 技术与职责 |
| --- | --- |
| 界面 | React 18、TypeScript、Vite、Recharts |
| 业务服务 | FastAPI、Cloudflare Workers；角色、状态流转、版本校验与审计 |
| 数据 | Cloudflare D1，账号与业务分库；SQLite 仅用于明确隔离的测试路径 |
| 风险分析 | XGBoost、SHAP、EWMA 与规则参考 |
| 排程 | Python OR-Tools CP-SAT；Workers 原生最早可行安排策略 |
| 助手 | 内置 Agent Harness、可配置 Dify Workflow |

```text
src/                    界面、导航、数据交互与助手
backend/                Python 业务接口、模型分析与维护排程
cloudflare/             Workers 账号、数据与原生工单服务
config/                 模型训练与助手配置
data/model-validation/  冻结的软件验收输入
scripts/                启动、迁移、测试与验收工具
tests/                  后端回归测试
deploy/                 云端部署与数据库结构配置
docs/                   操作、设计、模型与部署说明
```

## 验证依据与当前边界

### 冻结软件验收数据

| 项目 | 内容 |
| --- | --- |
| 文件 | `data/model-validation/dataset.json` |
| 数据身份 | `model-validation-v1-4141a127f218` |
| 来源 | `SYNTHETIC_CNC_MODEL_VALIDATION_V1` |
| 规模 | 24 台合成机床、34,560 条监测记录、144 次合成故障 |
| SHA-256 | `4141a127f218e19c11e3231e8f5c1910fb13426d9b14623fb645c89a9861a947` |

监测值与故障标签冻结，载入时核验摘要；明确标识的模拟班次、订单与停机窗口可随演练日期调整。此数据用于复现软件行为与流程检查。企业文件导入成功不代表模型已适用于该企业。

### 如何理解结果

- **风险分数用于复核排序**，未经概率校准，不能直接当作未来故障概率或经济收益计算依据。
- **SHAP 展示模型特征贡献**，不证明设备故障的物理原因。
- **模型评估区分采样窗口与独立故障事件**；首次命中提前量不等于持续稳定预警，提醒数也不等于现场出勤数。
- **三方案比较使用相同资源条件**；CP-SAT 优先优化维护优先级总分，不承诺企业综合经济收益最优。
- **当前验证主要覆盖软件与约束流程**；真实人员试用、操作用时、现场预测效果、停机与经济收益、干净 Windows 安装及物理断网仍需专项验证。本地启动也依赖云端 D1。

### 验证命令

以下用于开发与隔离验收，不是首次体验必需步骤；先按对应脚本要求准备隔离环境。

```powershell
.venv\Scripts\python.exe -m pip install -r backend/requirements-test.lock.txt
.venv\Scripts\python.exe -m pytest -q -p no:cacheprovider
npm run test:client
node scripts/test-operational-tasks.mjs
node cloudflare/identity/test-work-orders.mjs
npm run build
.venv\Scripts\python.exe scripts/final-acceptance.py
```

最终验收脚本在隔离数据库中检查模型证据、数据质量、只读预览、方案保存、联合排程与工单生命周期，报告输出至 `outputs/final-acceptance/report.json`。隔离测试通过不等同于线上 D1、完整云端部署或现场效果已验收。
