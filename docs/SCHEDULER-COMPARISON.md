## 复现

在仓库根目录，准备 Python 3.12 与 Node 24：

```bash
python -m venv .venv-comparison
. .venv-comparison/bin/activate
python -m pip install -r scripts/requirements-scheduler-comparison.txt
PYTHONPATH=. python -m pytest --noconftest tests/test_scheduler_comparison.py tests/test_joint_schedule.py -q
```

实际环境以原始 JSON 为准。此处使用隔离依赖目录并通过 PYTHONPATH 引用上述固定版本；12 项定向测试通过。`--noconftest` 有意不加载全应用数据库 fixture，这些测试只调用纯排程/校验函数，没有进行数据库或线上写入。未运行全套应用回归、Miniflare/D1 工单生命周期与 Cloudflare 边缘运行时性能测试。

## 同条件口径

- [唯一固定输入](../tests/fixtures/scheduler-comparison.json)明确记录任务、人员、技能、班次、生产占用、全局库存、预算、累计维护工时、并发人数、起算时间和固定时钟。所有时刻为上海本地时间；Workers 内部转为 +08:00，Python 使用同一无时区本地墙钟。没有当前日期漂移。
- Workers 适配器调用 `work-orders.mjs` 的真实生产 route，复用 candidate/place/库存与预算检查，不复制贪心算法。只替换数据库状态和写入方法为内存快照，无外部副作用；生产文件仅新增测试导出。Python 调用真实 `schedule_selected(..., allow_subset=True)`，由统一库存生成每项 available_quantity，没有另设资源容量。
- 当前 Workers 手工工单按高/中/低、创建顺序排序，并非预测风险排序。统一评价权重为高 9000、中 6000、低 3000；Python priority_score 映射为 .9/.6/.3，Workers 保留真实类别排序。其 candidate 返回的固定 .6 不参与统一评分。权重是事先指定的模拟效用，没有货币意义。
- 双方每次独立进程总预算均为 15 秒，串行执行、同一 CPU 亲和，重复 3 次并交替先后顺序；CP-SAT 保持生产默认内部 10 秒上限，单线程、随机种子 0。相同外部额度不表示相同工作量或算法必须耗尽额度。超预算记 PROCESS_TIMEOUT 并使运行失败，不得标为无解。
- elapsed_ms 包含 Node/Python 进程启动与依赖导入，是可复现命令级耗时；algorithm_ms 从生产 route/排程函数调用前计时，排除进程和初次依赖导入，保留各自真实输入检查与建模工作。两种指标同时记录，不把此处本地 Node 速度当作边缘网络响应时间。3 次样本只报告中位数，没有显著性结论。
- 单一资源评价器从原始任务重新计算成本、维护时长、人员工时、类别覆盖、权重、库存消耗、未安排任务和利用率；检查任务身份/重复、时长、设备窗口、起算下界、技能、班次、人员累计工时、团队人数、人员/设备重叠、生产占用、并发人数、库存、总预算和累计维护工时。校验器不信任算法返回的 cost/hours/priority 或 selection 汇总。恶意改坏输出的回归测试验证校验器会拒绝约束违规。
- 所有任务独立、可选；无已有活动工单、无库存预留、无未知配置。本次只验证这一共同支持的子域。输入 expected 仅冻结人工检查过的小用例覆盖与权重作为回归期望；它不是另一个最优性证明器。机器约束校验发现违规、期望回归或进程超时均使命令返回非零。

## 状态、无解与未验证范围

Workers `feasible` 表示找到了原生策略计划，`no_plan` 仅表示该策略没有安排任务，不能证明全局最优或全局无解。CP-SAT 的实际状态由包装真实 CpSolver.solve 记录，保留 objective、best_bound 与求解器 wall time；包装只固定线程、种子和已有时间上限，不改变模型与求解结果。OPTIMAL 仅表示当前编码的有限模拟模型最优，包括生产实现的优先级目标和完成时间次目标，不能推导真实业务最优。

`no_nonempty_plan`（无合格技能）与 `changed_stock`（零库存）均由输入预检拒绝所有任务：CP-SAT 记 PRECHECK_NO_CANDIDATES，没有调用求解器，不伪造 INFEASIBLE。由于允许子集，空计划始终是可行候选，本次没有强制所有任务必须安排的不可满足性证明。库存由 0 恢复到 2 后两种策略均重新安排两项，证据不复用旧计划。生产冲突用例 A 全窗口被占用，B/C 仍能安排。

未安排原因保留生产算法原文：Workers 提供先遇到的预算、库存或时窗原因；Python 对未选任务可能只提供联合约束的汇总原因。这些是实现解释，不是经过独立因果证明的唯一排除原因，不强行映射为相同根因。外部超时会单独标记。本次没有真实求解超时；现有 test_joint_schedule.py 通过注入 UNKNOWN 验证“超时不等于无解”的文案边界。
